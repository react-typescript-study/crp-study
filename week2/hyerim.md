# 2주차. 브라우저 렌더링 성능 진단 – DevTools로 병목 파헤치기

## 1. Performance 타임라인 — Composite 단계가 사라진 이유

최신 브라우저의 Performance 탭에서는 `Composite` 단계가 명시적으로 보이지 않는 경우가 있다. 강의에서는 Layerize, Commit 등 합성에 관련된 다른 작업과 함께 처리되어 보일 수 있다고 설명했다.

CRP의 개념적인 단계와 DevTools에 표시되는 작업 이름이 항상 일치하는 것은 아니다. Composite라는 이름이 보이지 않아도 내부적으로 화면 합성은 이루어진다.

| 작업 | 역할 |
| --- | --- |
| Layerize | 브라우저가 합성에 사용할 레이어 구성을 결정하는 과정 |
| Commit | 메인 스레드가 준비한 레이어 등의 상태를 컴포지터 측으로 전달하는 과정 |
| Composite | 준비된 여러 레이어를 합쳐 최종 화면을 만드는 과정. GPU가 활용된다. |

Layerize와 Commit은 합성으로 이어지는 작업이다. 다만 이 두 작업이 기록됐다는 것만으로 화면 표시까지 완료됐다고 볼 수는 없다.

## 2. Layout Shift & CLS — 화면 흔들림 측정하기

### 이미지 로딩 전에 공간 예약하기

이미지가 로딩된 후에야 크기가 정해지면 주변 요소가 밀리면서 Layout Shift가 발생할 수 있다.

이미지에 `width`와 `height`를 지정하면 브라우저가 로딩 전에도 비율에 맞는 공간을 미리 확보할 수 있다.

```html
<img src="image.jpg" width="800" height="450" alt="이미지 설명" />
```

**Performance 탭에서도 Layout Shift가 어디서, 얼마나 발생했는지 확인할 수 있다.** CLS(Cumulative Layout Shift)는 이런 예기치 않은 화면 이동으로 인한 시각적 불안정성을 측정하는 지표다.

### 웹폰트도 Layout Shift를 일으킨다

대체 폰트에서 웹폰트로 바뀔 때 글자 크기나 줄바꿈이 달라지면서 Layout Shift가 발생할 수 있다.

- `preload`: 웹폰트를 미리 요청해 늦게 로딩되는 상황을 줄인다.
- `font-display: swap`: 대체 폰트로 텍스트를 먼저 보여주고, 웹폰트 로딩이 끝나면 교체한다.

다만 **swap은 폰트 교체 시 Layout Shift가 생길 수 있다.** 화면 흔들림을 줄이려면 대체 폰트와 웹폰트의 크기 차이도 고려해야 한다.

### transform과 opacity가 부드러운 이유

`transform`과 `opacity` 애니메이션은 조건이 맞으면 Layout과 Paint를 건너뛰고 합성 단계에서 처리될 수 있다.

매번 요소의 크기와 위치를 다시 계산하고 다시 그리는 대신, 이미 그린 콘텐츠의 위치나 투명도를 바꾸므로 부드러운 애니메이션에 유리하다.

## 3. Paint Flashing & Layer Borders — 렌더링 시각화 실습

### Paint flashing 켜보기

DevTools의 Rendering에서 Paint flashing을 켜면 다시 칠해지는 영역이 초록색으로 깜빡인다. Layer borders를 켜면 레이어 경계도 확인할 수 있다.

화면에서 어떤 부분이 다시 그려지는지 눈으로 확인할 수 있다.

### Hover 효과의 비용

Hover 상태에 들어가거나 나갈 때 스타일이 바뀌면 그에 맞는 렌더링 작업이 발생한다.

- `width`, `height` 등을 바꾸면 Layout과 후속 Paint가 발생할 수 있다.
- 배경색이나 그림자를 바꾸면 Paint가 발생할 수 있다. 특히 넓은 영역의 blur나 그림자는 그리는 비용이 커질 수 있다.
- 이런 속성에 transition을 걸면 시작과 끝뿐 아니라 중간 프레임에서도 작업이 반복된다. 여러 카드 위로 포인터를 빠르게 움직이면 효과가 겹쳐 실행될 수도 있다.

**Hover 상태를 유지한다고 계속 Repaint가 발생하는 것은 아니다.** 스타일 변화나 transition이 끝난 뒤에는, 다른 변화가 없다면 포인터가 그대로 올라가 있어도 추가로 다시 그릴 필요가 없다.

따라서 Hover 개수 자체에 제한이 있는 것은 아니다. 넓은 영역이나 고비용 효과를 자주 애니메이션하는 경우가 문제이며, 단순한 색상 변경까지 피할 필요는 없다. Paint flashing으로 다시 그리는 영역을 보고 Performance에서 실제 비용을 확인한다.

### GPU 레이어 분리: 최적화와 주의사항

CSS 애니메이션 최적화 전략 중 하나는 움직이는 요소를 별도 합성 레이어로 분리해 처리하는 것이다.

레이어 분리에 영향을 줄 수 있는 속성은 다음과 같다. 다만 이 속성이 있다고 항상 별도 레이어가 생성되는 것은 아니다.

- `transform`
- `opacity`
- `will-change`
- `position: fixed`

레이어를 너무 많이 분리하면 오히려 성능이 떨어질 수 있다.

- GPU 메모리 사용량 증가
- 합성 단계에서 불필요한 오버헤드 발생
- 전반적인 렌더링 성능 저하

## 4. FPS & 렌더링 타임라인 — 애니메이션 성능 분석

FPS가 떨어지는 이유는 브라우저가 한 프레임을 준비하는 데 너무 오래 걸려 다음 화면 갱신 시점을 놓치기 때문이다.

예를 들어 60Hz 화면에서는 약 16.7ms마다 새 프레임을 표시해야 한다. 필요한 작업이 그 안에 끝나지 않으면 프레임이 늦게 표시되거나 건너뛰어져 애니메이션이 버벅이는 것처럼 보인다.

Performance의 프레임과 작업 기록을 함께 보면 어느 순간에 프레임이 늦어졌고, 그때 어떤 작업이 오래 걸렸는지 확인할 수 있다.

### 여러 프레임을 미리 준비하고 실행할 수는 없을까?

정해진 장면을 재생하는 애니메이션은 가능하다. 영상이나 스프라이트 시트처럼 프레임을 미리 만들어 두고, 필요한 이미지의 다운로드와 디코딩을 앞당겨 재생 중 대기를 줄일 수 있다. 대신 준비 시간과 메모리 사용량이 늘고, 준비된 프레임을 화면에 표시하는 작업은 여전히 필요하다.

웹 UI는 사용자의 입력, 스크롤, 창 크기에 따라 다음 화면이 달라진다. 가능한 모든 상태의 프레임을 미리 만들어 저장하기는 어렵다.

`transform`과 `opacity` 애니메이션에서는 이미 그린 콘텐츠를 재사용하고 위치나 투명도만 바꿀 수 있다. 프레임 이미지를 모두 저장하는 대신, 콘텐츠와 변화 규칙을 준비해 매 프레임 필요한 작업을 줄이는 방식이다.
